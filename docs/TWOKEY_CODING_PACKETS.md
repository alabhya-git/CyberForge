# TwoKey: bounded work packets for Codex or Claude Code

Use these packets during the event's authorized implementation window. They are specifications for future implementation; no application code has been generated by this planning task.

## Working agreement

Give the coding assistant the relevant packet, [build specification](TWOKEY_BUILD_PLAN.md) and existing repository context. Ask it to inspect current code before editing. Freeze shared schemas in Packet 01 before separate human workstreams edit dependent modules.

Use one working branch per human builder, short commits and a shared integration branch. One person owns shared contract changes. Integrate at the end of each packet, not at the end of the day. Model choice matters less than small interfaces, explicit failure behavior and real acceptance checks.

Each task should finish with changed files, verification performed, known gaps and commands to reproduce. Never accept a fabricated green dashboard as completion.

### Reusable instruction block

> Implement only the assigned packet against the current repository. Read the TwoKey build specification first. Use strict typed contracts and real fixture behavior. Treat model output and client text as untrusted proposals. Do not add an execution bypass, arbitrary URL replay, shell tool, real payment provider or cloud integration. Do not silently change shared schemas. Run the packet's meaningful acceptance checks and report failures. Use measured run artifacts for UI results. A stub must be explicitly labeled and cannot satisfy an end-to-end acceptance gate.

## Packet 01 — contracts and skeleton

**Owner:** B; A reviews. **Depends on:** nothing. **Timebox:** first two hours.

Implement strict models for EvidenceRecord, OperatorPolicy, ActionSpec, Proposal, PlanBundle, GateReceipt, ReplayReport, Counterexample, RunEvent and ExecutionResult. Define finite action/resource/service enums. Add canonical serialization and stable SHA-256 digests. Implement the run-state transition validator and event sequence numbers.

Canonicalization must specify UTF-8, sorted object keys, stable action ordering, timestamp format, no NaN/infinity and integer units for costs/times where possible. Do not hash an arbitrarily formatted JSON string supplied by a client. Receipt payloads must include a format version.

Scaffold health endpoints, configuration validation and the repository layout from the playbook. Provide a checked-in `.env.example` containing names and placeholders, not secrets. Add a tiny contract fixture usable by both frontend and backend.

**Acceptance:** equivalent canonical plans hash identically; changed actions/versions hash differently; unknown fields and action kinds fail; illegal state transitions fail. All services import the same contracts successfully.

**Assistant prompt:**

> Implement Packet 01. First propose the exact minimal schema fields from the specification, then implement them without expanding scope. Include canonicalization tests for reordered keys and modified actions, plus strict schema rejection tests. Export an OpenAPI schema and a small static fixture for frontend integration. Do not implement real containment yet.

## Packet 02 — synthetic commerce and deterministic detection

**Owner:** A. **Depends on:** 01.

Implement the commerce API, local payment ledger, inventory changes and idempotent checkout. Add synthetic aggregate and customer-export endpoints, seeded keys and reset/snapshot interfaces restricted to internal service credentials.

Implement gateway observation records with server-resolved credential and resource IDs. Client-supplied `X-Forwarded-For` or similarly named fields cannot overwrite authoritative peer/auth facts. Implement the documented export-authorization violation predicate. Keep raw request text separate from the normalized evidence facts.

Use a consistent snapshot operation. SQLite backup or a deterministic fixture export is preferable to copying a database file while it is being written. Live and shadow must use separate volumes.

**Acceptance:** checkout changes all relevant state exactly once; repeated idempotency key does not double-charge; fixture export actually returns a canary record before containment; benign aggregates do not create the incident; reset produces the same seed state; shadow writes do not affect live.

**Assistant prompt:**

> Implement Packet 02 with a real local ledger and synthetic data. Show the unauthorized effect and the independent policy predicate that detects it. Do not infer key compromise from the injected text. Add a smoke path that exercises checkout, export and reset through HTTP and validates database effects.

## Packet 03 — finite gateway policy engine

**Owner:** A. **Depends on:** 01–02.

Implement deny rules for credential/resource, credential/global, path, resource/global and mapped service scopes. Resolve canonical resources consistently with the app route manifest. Normalize paths using the actual HTTP framework behavior and test aliases/encoding before making claims about them.

Compose rules as a monotonic deny union. Store immutable revisions. The protected gateway initially has a closed policy-mutation endpoint that accepts no writes until Packet 07 is complete. Shadow and baseline administration use different endpoints and credentials on separate instances.

**Acceptance:** required policy rules change actual HTTP outcomes; policies survive restart; readers see one complete revision; unrelated service paths remain unchanged; no protected mutation path accepts a shadow/baseline token.

**Assistant prompt:**

> Implement Packet 03. Use a fixed action catalog with deterministic rule compilation and atomic policy snapshots. Preserve a closed protected-live mutation boundary until the two-receipt verifier exists. Do not implement a debug bypass to simplify tests; test through an isolated shadow instance.

## Packet 04 — Key 1 and investigator adapter

**Owner:** B. **Depends on:** 01–02; action IDs agreed with 03.

Implement the evidence-to-action verifier as a pure function returning allow/deny and structured reason codes. Add deterministic catalog enumeration. Implement a provider adapter that sends the security task, normalized evidence and explicitly delimited untrusted text to the selected model and parses a strict Proposal.

The model receives no tools. A separate optional extractor must preserve taint. Model explanations may not create evidence, authorize targets or close an incident. Store raw model output, parsed proposal, validation errors and model settings for audit.

Add a recorded adapter and disabled mode with visible mode metadata. No hidden cached/live switching.

**Acceptance:** valid scoped denial passes; forged evidence, wrong target, wrong incident, old epoch, unknown action and attacker-derived authority fail. A malicious “ignore the incident” response does not prevent deterministic candidate enumeration.

**Assistant prompt:**

> Implement Packet 04. Prioritize semantic authorization over prompt wording. Include a test where the model cites a real evidence ID but chooses the payments target: it must fail. Include a schema-valid extracted target that remains tainted. Do not treat successful JSON parsing as a trust upgrade.

## Packet 05 — Z3 planner and independent oracle

**Owner:** B. **Depends on:** 03–04.

Implement modeled attack coverage and business breakage for each catalog action. Use Boolean action variables, hard attack/business constraints and lexicographic objectives. Compute disruption costs per affected workflow so overlapping actions do not double-count.

Add a test-only exhaustive oracle for six to eight actions. Add named constraints for a meaningful conflict explanation using a companion solver when needed. Return typed feasible, infeasible, timeout and error outcomes.

**Acceptance:** solver objective matches the exhaustive oracle across selected small cases; deny-all fails protected workflows; do-nothing fails attack coverage; S3 is infeasible; timeouts are not reported as infeasible or optimal.

**Assistant prompt:**

> Implement Packet 05 using the installed Z3 API and the fixed catalog. Keep unauthorized actions out of the selectable set. Validate solutions independently with subset enumeration in tests. Return a structured explanation of chosen actions and rejected business constraints. Do not add 40 dummy actions for presentation.

## Packet 06 — shadow replay and Key 2

**Owner:** A. **Depends on:** 02–03 and 01 contracts.

Build the replay runner with fixed internal destination mappings, per-request and total deadlines, reset-before-candidate semantics, semantic attack oracles and business assertions. Validate baseline fixture health and attack effectiveness before certifying the candidate.

Implement report serialization, report digests and the Key 2 receipt. The receipt must be issued only after every required assertion completed successfully. Key 2 secret exists only in verifier and protected executor configuration.

**Acceptance:** safe narrow deny passes; checkout breakage, leaked canary despite misleading status, forbidden side effect, missed route alias, runner timeout and empty suite all fail. Report captures the exact failing request/assertion. No external URL can enter replay.

**Assistant prompt:**

> Implement Packet 06. Exercise actual HTTP services and inspect ledger/record effects. A list of expected booleans is not a replay. Return a Counterexample when the model and observed behavior disagree. Keep the verification report tied to the exact plan, image/configuration and suite version.

## Packet 07 — binding, application and recovery

**Owner:** A, with B reviewing Key 1 receipt production. **Depends on:** 04–06.

Finalize the PlanBundle, rerun Key 1 on the selected actions and sign its receipt. Implement protected executor verification of both keys, expiry, digest, relevant epochs, expected revision and idempotency. Use distinct standard HMAC secrets; compare signatures in constant time.

Implement transactional policy persistence and atomic in-memory swap. Add post-apply probes, a quarantine overlay and verified supplementary rollback. Reset-lab is a separate operation with a separate UI label.

**Acceptance:** missing/swapped/stale/tampered receipts are rejected; one of two concurrent changes wins; retrying the identical applied plan returns its prior result; a conflicting retry fails; safe rollback preserves containment; restart loads the committed policy.

**Assistant prompt:**

> Implement Packet 07. Treat the executor as the final security boundary. Verify receipts independently at the gateway instead of trusting a control-server flag. Include a test changing one action after both approvals, a test changing policy revision before apply, and a test proving rollback does not reopen the compromised export path.

## Packet 08 — orchestration and operator workspace

**Owner:** B. **Depends on:** 01, 04–07; UI shell can start earlier.

Implement durable run events, single-run locking, bounded stage deadlines and SSE updates. Connect the UI to measured business/attack outcomes. Show Key 1 rule failures, Key 2 per-assertion results, selected scope and exact current policy revision.

Add a compact evidence drawer and a clear model-mode label. Render all raw strings as escaped text. Requirements edits create a new policy version and invalidate pending approvals. An interrupted/restarted control process cannot silently resume an old approval as current.

**Acceptance:** browser reconnect resumes events; run state reflects backend failures; no result counters are hardcoded; requirement changes invalidate a ready plan; button state prevents duplicate starts but server idempotency still handles retries.

**Assistant prompt:**

> Implement Packet 08 as one incident workspace. Prioritize measured checkout health, exposed synthetic records, both gate decisions and the applied policy. Use actual server events. Do not display success from elapsed time or optimistic animation. Keep raw model output in an optional escaped drawer.

## Packet 09 — baseline, refinement and evaluation

**Owners:** A handles replay cases; B handles model runner/reporting. **Depends on:** 08 primary scenario stable.

Implement the isolated unguarded reference gateway and reasonable reference-agent prompt. Add S2 route-model counterexample and S3 incompatible requirements. Add frozen variant metadata, development/held-out split, benign controls and JSONL results.

Create report generation from raw artifacts with denominators, errors and architecture/model versions. Proposal-replay ablations must execute in the evaluation adapter. They cannot weaken protected-live.

**Acceptance:** primary 120-run protocol can resume without losing prior rows or duplicating case IDs; failures remain in the summary; counts match the manifest; recorded/fault-injected proposals never enter fresh-model statistics as if generated live.

**Assistant prompt:**

> Implement Packet 09 following the exact counting protocol in the execution playbook. Preserve baseline successes and TwoKey failures. Freeze input hashes before the final run. Add metrics for useful safe completion and false escalation so doing nothing or denying everything cannot score well.

## Packet 10 — deployment and release

**Owners:** joint. **Depends on:** primary acceptance gates.

Implement multi-stage image builds, pinned dependencies, internal networks, loopback-only local UI publishing, mounted secrets, health/readiness checks and a one-command smoke script. Build the frontend into control. Keep the baseline profile optional.

Write the setup guide, threat model, measured results, limitations, AI/third-party disclosures and demo script. Add optional remote configuration only after local release verification. Prepare live/recorded/disabled model modes with unmistakable labels.

**Acceptance:** a clean environment starts from documented commands; protected mutation/internal fixture ports are not public; local smoke passes; model outage has a visible fallback; exported artifacts contain no fixture secrets; the submitted commit matches the benchmark manifest or differences are disclosed.

**Assistant prompt:**

> Implement Packet 10 for local Docker Compose first. Use the deployment boundary from the playbook. Do not expose Docker administration or arbitrary replay destinations. Verify readiness and the S1 smoke path from a clean run, then document the exact commands and versions. Do not deploy externally unless separately requested.

## Final review questions

Before calling a packet complete, have the other human inspect the answer to the relevant question:

- Can attacker text change authority, target binding or incident status?
- Can a model hide the only useful candidate?
- Can a plan pass with no real attack or no real business assertion?
- Can receipts from one plan or environment authorize another?
- Can concurrent requests or restart skip the revision check?
- Can a rollback silently re-enable the compromised credential/resource path?
- Can UI counters disagree with stored artifacts?
- Can a baseline fault fixture be mistaken for a real model result?

Resolve demonstrated failures. Avoid adding architecture or features merely to increase the size of the codebase.
